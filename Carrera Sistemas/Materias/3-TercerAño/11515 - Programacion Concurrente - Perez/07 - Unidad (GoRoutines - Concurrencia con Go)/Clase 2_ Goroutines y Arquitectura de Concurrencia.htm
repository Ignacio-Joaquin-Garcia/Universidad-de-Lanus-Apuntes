Arquitectura y Fundamentos de Concurrencia

Programación Concurrente

Concurrencia vs Paralelismo

"La concurrencia es acerca de la estructura, el paralelismo es acerca de la ejecución".

Concurrencia

Manejar múltiples tareas que pueden ejecutarse al mismo tiempo. Es un concepto de diseño de software.

Paralelismo

Ejecutar múltiples tareas físicamente a la vez. Requiere hardware con múltiples núcleos.

Recursos Compartidos

Los hilos comparten el Heap, el código y las variables globales. Esto permite comunicación rápida pero requiere sincronización.

Estado Privado

Cada hilo mantiene su propio Stack y registros (Contador de programa) para su ejecución independiente.

¿Qué es una Goroutine?

Es un hilo de ejecución ligero gestionado íntegramente por el runtime de Go.

Stack Dinámico

Inician con 2KB y crecen según necesidad. Mucho más eficientes que hilos tradicionales.

M:N Scheduling

Multiplexa miles de Goroutines sobre pocos hilos del SO de forma inteligente.

Bajo Costo

Context switch ultra rápido en espacio de usuario, sin intervención del Kernel.

Lanzando Goroutines

Usamos la palabra clave go. Esto indica al Scheduler que ejecute la función de forma asíncrona.

Punto Crítico

Si la función main termina, todas las demás Goroutines se detienen instantáneamente.

func saludar(n string) {
    fmt.Println("Hola", n)
}

func main() {
    go saludar("Estudiantes") 
    
    // El programa terminará antes de
    // que la goroutine pueda imprimir.
    fmt.Println("Fin del programa")
}

El Problema: time.Sleep

Incorrecto: time.Sleep

Adivinar tiempos es imposible y frágil bajo carga de servidor.

Correcto: WaitGroup

Espera determinística. El programa dura exactamente lo necesario.

// ❌ EVITAR: Adivinar
go trabajar()
time.Sleep(time.Second)
// ✅ USAR: sync.WaitGroup
var wg sync.WaitGroup
wg.Add(1)
go func() {
    defer wg.Done()
    trabajar()
}()
wg.Wait()

Control de Flujo: defer

"Pospone la ejecución hasta que la función contenedora retorna."

¿Para qué sirve?

  • Liberar Mutex / Locks.
  • Cerrar archivos o sockets.
  • Notificar fin de tareas (WaitGroups).
  • Garantizar limpieza incluso con panic.

Se ejecutan en orden LIFO (Last In, First Out).

func proceso() {
    defer fmt.Println("1º: Limpieza final")
    defer fmt.Println("2º: Cierre recursos")
    fmt.Println("Trabajando...")
}

// Salida:
// Trabajando...
// 2º: Cierre recursos
// 1º: Limpieza final

Sincronización Determinística: WaitGroup

sync.WaitGroup es un contador que bloquea el flujo hasta que llega a cero.

Add(n): Registra tareas pendientes.
Done(): Indica que una tarea terminó.
Wait(): Bloquea hasta que el contador es 0.
var wg sync.WaitGroup

wg.Add(1)
go func() {
    defer wg.Done()
    tareaPesada()
}()

wg.Wait() // Main espera aquí

Goroutine Leaks (Zombis)

"Una Goroutine bloqueada para siempre es memoria que nunca se recupera."

Causas

Esperar por canales que nadie escribe o bloqueos infinitos en WaitGroups.

Consecuencia

Agotamiento de RAM (OOM Killer) en aplicaciones de larga duración.

Arquitectura del Scheduler: M:P:N

M

MACHINE

Hilos reales del Sistema Operativo. Limitados (típicamente = CPUs).

P

PROCESSOR

Contextos lógicos. Controlados por GOMAXPROCS (por defecto = CPUs).

G

GOROUTINE

Nuestras tareas. Potencialmente millones. Distribuidas en Ps.

Relación

Típicamente: 1 M : 1 P : N Gs
Ejemplo: 8 CPUs = 8 Ms = 8 Ps, pero millones de Gs distribuidas.

Work-Stealing

Si un P se queda sin Gs, roba trabajo de otra P para evitar ociosidad. Máxima eficiencia.

Visualizar: GOMAXPROCS indica cuántos Ps activos. Cambia dinámicamente con runtime.NumCPU()

Hilos OS (Java) vs Goroutines (Go)

Java / C++ Threads

  • Peso: Stack fijo (~1MB).
  • Gestión: Kernel del Sistema Operativo.
  • Costo: Cambio de contexto caro (Modo Kernel).
  • Mapeo: 1 Hilo Java : 1 Hilo OS.

Go Goroutines

  • Peso: Stack dinámico (~2KB).
  • Gestión: Go Runtime (Espacio de Usuario).
  • Costo: Cambio de contexto muy barato.
  • Mapeo: N Goroutines : M Hilos OS.

Errores Comunes y Soluciones

Error: Captura de Variable

for i := 0; i < 3; i++ {
    go func() { fmt.Println(i) }() // Imprimirá 3, 3, 3
}

Solución: Pasar por Parámetro

for i := 0; i < 3; i++ {
    go func(v int) { fmt.Println(v) }(i) // Correcto
}

Error: WaitGroup fuera de tiempo

wg.Add(1)
go func() { // Olvidar wg.Done()
}()
wg.Wait() // DEADLOCK!

Solución: Defer Done

wg.Add(1)
go func() {
    defer wg.Done()
    // ...
}()
Siempre usa el Race Detector de Go corriendo tus tests con el flag -race.

Patrón: Procesamiento por Lotes

func main() {
    datos := []string{"A", "B", "C"}
    var wg sync.WaitGroup

    for _, d := range datos {
        wg.Add(1)
        go func(v string) {
            defer wg.Done()
            procesar(v)
        }(d) // ¡Importante: pasar por copia!
    }

    wg.Wait()
    fmt.Println("Lote finalizado")
}

Resumen: Clase 2 🎯

✓ Fundamentos

Las Goroutines son hilos ligeros gestionados por Go Runtime, no el SO. Permiten escribir código concurrente sin sacrificar eficiencia.

✓ Sincronización

WaitGroup + defer es la pareja ganadora: registro de tareas, espera determinística y limpieza automática de recursos.

✓ Evitar Trampas

Nunca uses time.Sleep para sincronización. Evita goroutine leaks siendo explícito con ciclos de vida y bloqueos.
